## The project
Multi-tenant **headless booking backend** in `backend/` (FastAPI, SQLAlchemy 2 async, PostgreSQL 16 + PostGIS, Redis, Alembic). It is the back end of a WordPress plugin and usable on its own. Five business types: staff-based (spa, clinic), restaurant, salon (with add-ons), automotive workshop, field service / professionals. Blueprint documents are in this folder (`BookingWebsiteBackendBlueprint_6th_Version.docx` is the latest, built 2026-10-14; it already stops before the second review's fixes, see *Documents*).

State today: migrations **0001-0033**, **2,607 tests** (ten consecutive clean full runs on 2026-10-21, after the price-after-inspection setting, see below; every finding of both reviews is fixed or recorded as a decision), `mypy app` clean (101 files). Every feature was mutation-tested.

Next: offer findings 2, 3, 4. No docx touched.
1. **HIGH, customer takeover (fixed, see status above).** `booking._upsert_customer` lets any public booking replace an existing customer's name and email (keyed by phone, no sign-in needed). Booking with a victim's phone and your own email makes `POST /public/auth/magic-link` for your email sign you in as the victim (their bookings, addresses, vehicles, PDPA data) and sends the victim's later messages (cancelled, reminders) to you. The victim cannot fix it: the profile endpoint only edits gender. Pre-registering a phone that has never booked works the same way. Fix options: never replace an existing email (keep the booking's own email on the booking, new column `bookings.contact_email`); and/or make an email count for sign-in only after it was confirmed by someone who proved they hold the phone.
2. **MEDIUM, one failing channel holds back the booking's other messages (FIXED 2026-10-14: migration 0030, status `refused`, `PermanentDeliveryError`; narrow code lists in README *Notifications*; 45 tests, 35 mutants all caught but one equivalent, ten runs clean at 2,367; a transient failure still retries and keeps the order, by design; code lists come from provider docs, not live messages).** The outbox keeps one booking's events in order, and any failure is retried six times, so a WhatsApp number that is not on WhatsApp (a permanent refusal) held "Your booking is confirmed" back by 15 min 35 s and made six gateway calls. Fix: treat a gateway or SMTP refusal as permanent (log `failed`, do not retry, do not block).
3. **MEDIUM-LOW, no duplicate protection (FIXED 2026-10-14: optional `Idempotency-Key` header, migration 0031; README *Sending a booking twice*; 27 tests, 32 mutants all caught but one equivalent, ten runs clean at 2,394; without the header nothing changes, so the widget must always send one; a guess for duplicates without a key was deliberately NOT built because one phone can book two people for the same time).** The same booking request sent twice (double click, retry after a timeout) gives two bookings (two staff at the same time with "any available"), and both count against the free plan's monthly bookings. Fix: an `Idempotency-Key` header and/or a 409 for the same customer at the same start.
4. **LOW, no time check on status moves (FIXED 2026-10-14: `booking.ensure_status_time`, `STATUS_EARLY_MINUTES` default 60; no-show only from the start, in-progress/completed from 60 min before, completed from in-progress any time; no migration; README *Status moves and the clock*; 32 tests, 25 mutants all caught, ten runs clean at 2,426; the rest of the suite runs with the rule switched off by the `no_status_timing` fixture in conftest; no manager override was built).** A confirmed booking next week can be marked `no-show` (frees its slot) or `completed` (frees it and sends "Thank you for visiting us" with the review link); an existing test relies on the latter. Fix: allow `in-progress`, `completed`, `no-show` only from shortly before the start.
5. **LOW, from reading only, not tested** (the first and third are limits recorded since the message-count fix): the business's message lock is held across the gateway call in `_notify`, so a sign-in code on a limited channel (WhatsApp, SMS) waits behind a slow gateway; one transaction per event, so a crash after the first channel sent repeats it (documented at-least-once); a sign-in code row left `sending` by a crash counts for the month for good; `sweep_all` goes through businesses one after another with 10 s gateway time-outs, so one dead SMTP server slows every business (bounded by the back-off); an add-on can lengthen a running appointment past closing time or the stylist's shift (only other bookings are checked, by design); a restaurant table with a non-numeric `minimum_spend` attribute would answer 500.
Found sound: the lost-race and deadlock handling, hold expiry, row locks on every status change, ownership checks (someone else's booking is a 404), instants (not clock readings) compared across daylight saving, once-only reminders and the stale-reminder skip, outbox ordering with `skip_locked`, header and template injection, the strictest-policy merge, atomic stock deduction, the review-flag rules.

## Traps learned (also in the memory notes)
- Never run two pytest processes against the one test database at once (a mutation run and a full run corrupt each other). A mutation that makes tests hang must count as caught (timeout).
- A run that takes many times longer than its neighbours means the laptop slept (connections die): repeat it. The "flake" of 2026-10-02 was almost certainly that.
- The Write tool says "updated" (not "created") when it overwrites an existing file: check `ls tests` before naming a new test file (`tests/test_security.py` already existed).
- Bash heredocs corrupt Python strings containing backslash sequences: write patch scripts with the Write tool. Line endings are a mix of LF and CRLF per file; count them with Python, not `grep -c $'\r'`.
- FastAPI 0.141 nests routers: list routes through `app.openapi()`, not `app.routes`.
- The helper scripts used for patching, mutation testing and the ten-run batches (`patchlib.py`, `mutate_*.py`, `roundtrip2*.py`, `tenruns_obs.sh`) lived in the previous session's scratchpad and may be gone; they are easy to recreate (an exact-text patcher; a list of mutants applied one at a time with the tests run and the file restored; one result file per full run).
